1. What the system does

The project is an internal analytics chatbot for WEBXPAY, a Sri Lankan payment gateway. A logged-in business user types a plain-English question (e.g. "What was the IPG revenue for March 2025?" or "Monthly GMV trend for 2025"), and the system:

  1. Understands the intent (which metric, which channel, which date range, which grain).
  2. Builds a safe, read-only SQL query — usually from hand-tuned templates, occasionally LLM-generated.
  3. Runs it against the live MySQL production-analytics database.
  4. Returns a natural-language answer + a data table + auto-generated charts.
Design philosophy: The LLM is used as a router and explainer, not as a free-form SQL engine. The financially-sensitive metrics (GMV, Revenue, MDR) are computed with fixed, Power-BI-verified SQL templates so numbers are deterministic and trustworthy. The LLM only fills gaps.

4. Authentication & session layer — auth.py

Self-contained auth on a local SQLite DB (auth_users.sqlite3) with two tables:

  • users — username, email, password hash (Werkzeug), role (adminuser), is_active, timestamps.
  • chat_sessions — per-user saved conversations (messages_json) with last-write-wins sync via a client_updated_at counter.

How it protects routes

  • @login_required — wraps a view; redirects browsers to /login, returns 401 JSON for API//ask calls.
  • @admin_required — same, but also requires role == "admin" (used for /users and user management APIs).
  • Session stored in a signed Flask cookie (HTTPOnly, SameSite=Lax; Secure if SESSION_COOKIE_SECURE set).
First-run bootstrap: When the users table is empty, signup_enabled() returns true so the very first account can self-register and is automatically made admin. After that, signup closes and only admins can create accounts. Default secret_key is "change-me-before-deploying" — must be overridden in production.

Auth-related routes

5. Web / API layer — app.py

Thin layer. Its real job is to call handle_user_question() and then normalize the result into a stable shape the frontend can always rely on.

POST /ask — the main endpoint

  1. Reads question from JSON (requires login).
  2. Calls handle_user_question(question, run_sql) → a payload dict.
  3. Normalizes:
    • timeseries → always {grain, ipg:[], pos:[]} (errors moved to an errors key).
    • result → always a list[dict] (the table the UI renders). For "overview" answers it merges IPG+POS time-series rows on the grain key and adds combined_gmv/revenue/volume.
  4. Returns one JSON object: {question, sql, result, raw_result, timeseries, insights, response_type}.
All errors are caught and returned as a normal 200 with the error inside insights, so the chat never shows a broken request.

Other routes

  • POST /feedback — appends a 👍/👎 record (question, sql, insights) to feedback_log.json.
  • GET / — serves static/index.html (login required).

6. Database access & safety — db.py

  • Creates a MySQL connection pool (size 8) from .env credentials; falls back to a direct connect if the pool fails.
  • run_sql(query) is the single execution path used everywhere. Before running it enforces a read-only guard:
SQL safety guard (_is_read_only_select): strips comments/string-literals, then rejects anything that isn't a single SELECT/WITH statement, blocks all write/DDL keywords (INSERT, UPDATE, DELETE, DROP, ALTER, CREATE, …) and INTO OUTFILE/DUMPFILE. Any failure returns {"error": "..."} instead of executing.

Results come back as list[dict] (dictionary cursor); errors as {"error": str}. This shape is what every handler downstream expects.

8. Intent classification & the routing pipeline

Every question flows through handle_user_question(), which runs an ordered cascade of checks. Order matters — earlier, more specific patterns win so they aren't "swallowed" by broader ones.

Step 0 — classify_question() (pure Python, no LLM)

  • greeting → canned help message.
  • knowledge ("what is MDR?", "explain IPG") → one small Gemini call with embedded WEBXPAY context. No SQL.
  • data_query → everything else; continues down the pipeline.

Step 1+ — the data-query cascade (in priority order)

  1. Year comparison ("2025 vs 2026 GMV") → handle_year_comparison.
  2. Merchant onboarding ("new merchants onboarded") → onboarding SQL.
  3. GMV-drop diagnosis ("why did GMV drop between A and B") → per-merchant mover analysis.
  4. Active / non-transacting merchants by channel → dedicated merchant SQL.
  5. Merchant type (IPG-only / POS-only / both).
  6. Analytical / bucket (cohorts, activity buckets).
  7. Transaction status (approved / declined / abandoned / cancelled).
  8. Explicit time-series (grain + metric, e.g. "monthly GMV 2025") → IPG+POS in parallel, merged.
  9. Period overview / dashboard ("how was June", "give an overview") → handle_period_overview.
  10. Month comparison / anomaly ("does any month stand out") → overview path, full year.
  11. Top-N merchants → handle_top_merchants.
  12. Combined single-period (channel "both" + gmv/volume/revenue) → handle_combined_query (runs IPG + POS, sums).
  13. Fallback → cached SQL → generate_sql → generic LLM SQL.
Why so many branches? Each branch maps a class of business question to SQL whose numbers have been validated against Power BI. The cascade is effectively a hand-built intent router that keeps the financial math correct.

analyze_intent() — the structured read of a question

Returns a dict with: type (gmv / revenue / mdr / volume / count / pos / schema / generic), metric, date_start/date_end, currency_id, time_grain (day/week/month), and POS routing fields (channel, pos_metric). POS is auto-detected even without the word "pos" (e.g. "DFCC revenue").

9. SQL generation strategy

Three tiers, tried in order of trust:

TierMechanismWhen used
1. TemplatesHand-written builders (build_gmv_sql, build_revenue_sql, build_pos_*, time-series builders)All core financial metrics. Numbers are Power-BI verified.
2. LLM-refinedbuild_base_sql_candidates → refine_sql_with_llmQuestion close to a template but needs adjustment.
3. Generic LLMbuild_generic_sql (full schema in prompt)Last-resort, for questions no template covers.

Core domain formulas baked into templates

  • IPG GMV = sum of approved (payment_status_id = 2) order amounts in tbl_order, currency-filtered.
  • IPG Revenue = GMV × (merchant_rate − bank_rate) / 100 — the margin WEBXPAY keeps.
  • POS GMV / Revenue = from tbl_pos_transactions; revenue = t.mdr_rate − cost_rate (DFCC = provider 6, HNB = provider 5).
  • Volume = count of approved transactions.
  • Combined = IPG + POS run separately then summed (never a single naive join).
These definitions mirror dax_measures.py (the Power BI DAX library) so the chatbot's answers match the official dashboards.

10. Insight & answer generation

  • build_short_answer() — for simple single-number results, builds a deterministic sentence directly from the rows (no LLM, no risk of made-up numbers).
  • generate_insights() — for richer results, sends a compacted sample of rows to Gemini for a narrative summary. reasoning_effort="none" keeps it fast.
  • _compute_result_facts() — computes superlatives (highest/lowest/peak) and coverage over the full result set, then feeds those facts to the LLM so it can't get them wrong from a truncated sample.
No-fabrication guardrail: the answer layer is built so the bot never invents numbers and never refers to "the data you shared" — figures always come from the SQL result, and a sanitizer fixes the bot's voice.

11. Feedback, caching & self-correction loop

User clicks 👍 / 👎 ──► POST /feedback ──► append to feedback_log.json │ ┌──────────────────────────────────────────────┼───────────────────────────────────────┐ ▼ ▼ ▼ get_cached_sql() is_known_wrong() load_wrong_feedback() reuse SQL from a 👍 skip heavy path / regenerate inject "past mistakes" into near-identical question for a 👎 near-match the LLM prompt to avoid repeats
  • Positive feedback → get_cached_sql() reuses that SQL for near-identical future questions (word-overlap similarity ≥ 0.72), skipping LLM generation entirely — faster and consistent.
  • Negative feedback → is_known_wrong() makes the router avoid the previously-wrong path, and load_wrong_feedback() warns the LLM not to repeat the bad SQL.
  • query_cache.sqlite3 / summary_mart.sqlite3 are local cache/precompute stores for speeding up repeated queries.

12. Frontend — static/

No framework, no build step — one big index.html with embedded CSS/JS plus Chart.js from a CDN.

  • Auth bootstrap: checks /api/me; unauthenticated users are redirected to login.html.
  • Chat & history: conversations are stored per-user via /api/chat-sessions with last-write-wins sync; history is listed in a sidebar.
  • Rendering an answer: shows the insights prose, a data table from result, and the sql used (collapsible).
  • Auto-charts: buildChartConfig() inspects the result columns and auto-draws a Chart.js chart — including a dual-axis view for money-vs-count series — with bar/line toggles. Plain merchant-name lists are detected and skipped (no chart).
  • Feedback buttons: 👍/👎 post to /feedback, feeding the learning loop above.
  • users.html — admin-only screen to create users and toggle is_active.

14. End-to-end worked example

Question: "Monthly GMV trend for 2025"

  1. /ask receives the question (user is authenticated).
  2. classify_question → data_query.
  3. analyze_intent → type=gmv, time_grain=month, date_start=2025-01-01, date_end=2025-12-31, channel "both".
  4. Cascade hits the explicit time-series branch → builds build_ipg_timeseries_sql + build_pos_timeseries_sql and runs both in parallel.
  5. run_sql validates each as read-only and executes against MySQL.
  6. Rows are merged by month; generate_insights writes the narrative.
  7. app.py normalizes into {insights, result (12 merged rows), timeseries{grain:"month",ipg,pos}, sql}.
  8. Frontend renders the prose, a 12-row table, and a dual-axis monthly chart with bar/line toggle.

15. How to run & configure

Environment (.env)

DB_HOST=...            # MySQL analytics DB
DB_USER=...
DB_PASSWORD=...
DB_NAME=...

python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt   # flask, openai, mysql-connector-python, python-dotenv
python app.py                     # serves http://localhost:5000

First visit → register the first account (auto-admin) → start asking questions.

16. How to extend / maintenance notes

  • New metric or question type? Add a build_*_sql() template and wire a branch into the cascade in handle_user_question() (place it before any broader branch that would otherwise catch it).
  • Numbers wrong vs. Power BI? Compare the template's formula against the matching measure in dax_measures.py — that file is the spec.
  • Schema changed? Regenerate schema.txt so the LLM (and generic SQL fallback) sees the new tables/columns.
  • Switching LLM provider? Only the client = OpenAI(...) block and CHAT_MODEL in gpt_helpers.py need changing — everything else uses the OpenAI-compatible interface.
  • Security: set a real FLASK_SECRET_KEY, enable SESSION_COOKIE_SECURE, keep the read-only SQL guard intact, and never expose write credentials to db.py.
  • Watch-outs: the routing cascade is order-sensitive; keyword lists are broad by design — test new branches against existing question types to avoid regressions. The feedback loop is similarity-based, so very different questions with overlapping words can occasionally cross-match.
